# HANDBOOK.md — 運用ハンドブック

本MCPサーバーを実際に使う際の一般的な知見をまとめたものです。ツールの機能一覧は
`CAPABILITIES.md`、バージョン別の差分は `VERSION-NOTES.md` を参照してください。
ここでは「なぜそう作ってあるか」「実際に使うときにハマりやすい点」を扱います。

## スクリプトサーバー接続の仕組み

### 接続先とライフサイクル

- 接続先は既定で `127.0.0.1:9000`(環境変数 `ATOMCRAFT_HOST` / `ATOMCRAFT_PORT` で変更可)。
  Atom Craft本体を起動し、**スクリプトメニュー > サーバー > スクリプトサーバーを起動**
  した状態でないと接続できません。
- `robot.py` は接続先ライブラリ(DLL経由のRobot API)をバージョン依存パスから解決します。
  解決順は (1) 環境変数 `ATOMCRAFT_ROBOT_PATH` (2) サーバー本体隣接の `robot-path.txt`
  (3) `%USERPROFILE%\.atomcraft-mcp\robot-path.txt` の3段階。Claude Codeのプラグインは
  ユーザーのplugin cacheにコピーされて動くため、リポジトリ同梱のポインタファイルは
  インストール後には見えなくなります。そのため環境変数を第一の設定手段にしています。
- `AtomCraftTransport` はDLLの初期化(`initialize`)・接続(`connect`)・切断
  (`disconnect`)・完全リセット(`full_reset` = disconnect + finalize)の状態を管理する
  ステートマシンです。`full_reset` は世代カウンタ(`_generation`)をインクリメントし、
  タイムアウトした古いワーカースレッドの遅延書き込みが後から紛れ込むのを防ぎます
  (DLLが非スレッドセーフなため、呼び出し自体を強制終了できないことへの防御)。

### 実機で確認された接続断の挙動: クリーン切断は再接続可、まれにリスナーが停止することがある

**実機検証(Ver.3.57.02)で確認した運用知見です。** 当初は「スクリプトサーバーは
1接続限りで、1回の接続が終わると手動再起動なしには再接続できない」と解釈して
いましたが、追加の切り分け実験と実運用者の証言を踏まえ、この解釈は不正確だった
ことが分かりました。実際には次のように整理されます。

- **通常のクリーン切断(disconnect+finalize)後は再listenし、再接続できます。**
  連続2回の接続→ping→切断がすべて成功することを確認済みで、毎回の手動再起動は
  不要です
- **接続を保持したまま(ESTABLISHED)の状態でも、サーバー側のLISTENは継続します**
  (netstatで LISTENING と ESTABLISHED が同時に存在することを確認済み)
- **一方、スクリプトサーバーが停止して新規接続を受け付けなくなることがあります**
  (実測・実運用の両方で複数回確認)。異常切断やプロトコルエラー(不正な引数による
  PARSE_ERROR等)の後に起きやすい傾向はありますが、それが唯一の条件と断定できる
  ほどの根拠はなく、**発生条件は完全には特定できていません**(詳細な検証経緯は
  `verification-3.57.02.md` 参照)

したがって、次のような運用が実用的です。

- 通常の使い方では、都度再接続しても問題ありません。毎回の手動再起動は不要です
- **つながらなくなった場合**は、原因を厳密に特定できなくても対処は同じです。
  ユーザーにAtom Craft側で**スクリプトサーバーを手動で再起動**(スクリプトメニュー
  > サーバー > スクリプトサーバーを起動)してもらってください。`atomcraft_debug
  (action='reconnect')` はMCPサーバー側の状態(DLLのfinalize→再initialize→
  再connect)をリセットするだけで、Atom Craft側のスクリプトサーバーが停止して
  いる場合には効きません
- 接続断自体は例外やクラッシュを伴うものではなく、封筒(envelope)は常に正常な
  JSON形式で返ってきます。transport層のエラー分類自体は機能しているため、
  「エラーは返るが再接続できない」状態が続く場合は、この既知の挙動を疑って
  スクリプトサーバーの再起動を試してください

## エラー封筒の読み方

すべてのツールはJSON文字列を1つ返します。成功時は
`{"success": true, "data": ..., "message": ...}`、失敗時は
`{"success": false, "code": ..., "error": ..., "hint": ..., "retryable": ..., "details": ...}`
という統一フォーマットです(`envelope.py`)。

- **code**: 12種類に分類されます(`SERVER_UNREACHABLE` / `CONNECTION_LOST` /
  `TIMEOUT` / `INVALID_PARAMS` / `INVALID_FIELD` / `INVALID_TYPE` / `NOT_FOUND` /
  `ALREADY_EXISTS` / `PARSE_ERROR` / `UNKNOWN_OUTCOME` / `API_ERROR` /
  `UNSUPPORTED_VERSION`)。Atom Craft側の生のエラーメッセージ(日本語)を正規表現の
  パターン表で分類しており、パターンに一致しないものはすべて `API_ERROR` になります
- **hint**: 次にどう動けばよいかの具体的な案内。例えば `INVALID_FIELD` なら
  タイプ別の有効フィールド一覧と代替の取得経路(カテゴリは`get_property`では取れず
  `atomcraft_manage_category` を使う、等)を返します
- **retryable**: `true` なら機械的に再実行してよいという意味。`TIMEOUT` /
  `CONNECTION_LOST` / `PARSE_ERROR` は読み取り系であれば1回だけ自動リトライ済みです
- **UNKNOWN_OUTCOME**: 非冪等な書き込み操作(オブジェクト作成・削除など)の送信後に
  接続断・タイムアウトが起きた場合に返るコードです。**サーバー側では成功したか
  失敗したかを判別できていません。** そのまま同じ呼び出しを再実行すると二重作成
  等の副作用が起きる可能性があるため、必ず先に
  `atomcraft_get_object(method='find_by_name')` 等で対象が既に存在するかを
  確認してから、存在すればそれを使い、存在しなければ再実行してください

## UUID識別とfind_by_name

Atom Craft側のオブジェクトはすべてUUID文字列で識別されます。人間が扱う「名前」
から作業を始める場合は、まず `atomcraft_get_object(method='find_by_name')` で
UUIDを解決してから他のツールに渡してください。`ALREADY_EXISTS` エラーの hint も
同様に「`find_by_name` で既存オブジェクトのUUIDを検索し、見つかればそれを流用
してください」と案内しています(マテリアル登録など、名前が重複した場合の
定番の復旧パターン)。

## 日本語パス・cp932の罠

- `PARSE_ERROR`(Atom Craft応答の解析失敗)は読み取り系であれば自動リトライ
  されますが、繰り返し発生する場合は日本語パス起因である可能性が hint に
  明記されています
- ロボットAPI自体にも、関数引数に日本語などのマルチバイト文字を渡すと
  正しく処理されない不具合がVer.3.47.00〜Ver.3.55.02に存在し、Ver.3.55.03で
  修正されています(`VERSION-NOTES.md` Ver.3.55系を参照)。古いAtom Craftに
  日本語名を渡す作業では、この既知不具合を疑ってください
- ロボットのロード自体でも日本語パス絡みの落とし穴があります。CRI提供の
  `project.py` 等は内部で `import criatomcraft_api_lib` を非修飾で行っており、
  `robot-path` 直下だけでなく `cri/atomcraft` ディレクトリ自体もPythonの
  `sys.path` に加えないと `ModuleNotFoundError` になります。この不具合は
  fake_robotを使うユニットテストでは再現せず、実機接続で初めて発覚したもので、
  実機ではこの修正がないとサーバーが一切起動できない状態でした

## 大量呼び出しはサブエージェント委譲が安定

数十〜100回超のMCPコールを要する作業(キューシート一括構築、大規模プロパティ
一括変更など)を単一のセッションで直列に実行し続けると、コンテキストが
肥大化し判断品質が落ちます。ユニット/キャラクター単位でサブエージェントに
委譲し、各サブエージェントが1回分の作業を完走してから次のユニットへ進む
運用のほうが安定します。**並列接続の可否自体は未検証です**(同時に2接続を
張る実験は行っていません)。前述の通りスクリプトサーバーが停止して新規接続を
受け付けなくなることがあるため、安全側に倒して**単位ごとの逐次実行を推奨**
します。

## get_treeを先に呼ぶ

個々のオブジェクトに対して `get_object` → `get_property` を1件ずつ繰り返すと、
ツリーが大きい場合にAPI呼び出し数が線形に膨らみます。`atomcraft_get_tree` は
フォルダ階層を1回の呼び出しで再帰的に展開し、指定した `fields` を全ノード分
まとめて取得できます。まず `atomcraft_get_tree` で全体構造を把握してから、
個別の書き込みが必要な対象だけを `get_property` / `set_property` で扱う順序が
呼び出し数を大きく削減します。出力が `settings.tree_json_budget`
(既定50000文字)を超える場合はAPIを再呼び出しせずCSV+構造JSONの2ファイル
出力に自動フォールバックします。

## ツール更新時はATOMCRAFT_ROBOT_PATH差し替えのみ

Atom Craft本体をバージョンアップした場合、本MCPサーバー自体の再インストールは
不要です。環境変数 `ATOMCRAFT_ROBOT_PATH`(または `robot-path.txt`)が指す
`robot\remote\Python` のパスを、新しいバージョンのものに差し替えるだけで
接続先が切り替わります。新機能ツール(`atomcraft_preview` の新3action、
`atomcraft_manage_beatsync`、`atomcraft_bulk_property`)は接続先のRobot Python
に対象関数が実在するか(`hasattr`)と、`get_tool_version` で取得したバージョンが
下限を満たすかの二段構えでゲートされるため、古いバージョンのAtom Craftに
向けたままでもエラーメッセージ(`UNSUPPORTED_VERSION`)で安全に弾かれます。

## タイムアウト設計

- 既定のAPI呼び出しタイムアウトは `ATOMCRAFT_API_TIMEOUT`(既定30秒)。タイムアウト
  すると `AtomCraftTransport` はDLLをfull_reset(finalize→initialize)して健全化します
- `atomcraft_build` の `action=build` はビルド対象や規模によって数十秒〜それ以上
  かかりうるため、`timeout_sec` 引数でその呼び出し限りのタイムアウトを既定値より
  長く上書きできます
- **MCPクライアント側にも別のタイムアウト設定があることに注意してください。**
  例えばCodex CLI経由で利用する場合、クライアント側のツール呼び出しタイムアウト
  (`tool_timeout_sec` 相当の設定)が本サーバーの `timeout_sec` より短いと、
  Atom Craft側では処理が継続していてもクライアントが先にタイムアウトとして
  打ち切ってしまうことがあります。長時間かかるビルドを実行する際は、
  クライアント側のタイムアウト設定も合わせて緩めてください

## 制作運用の知見

本サーバー自体の実装から離れた、実際のキューシート構築作業で繰り返し確認されている
運用知見です。プロジェクト固有のスキルを書く・運用する際の判断材料として使って
ください。

### 台本・キューシート構築の型

**検証→構築→保存→再検証の4段フェーズ**: 台本スプレッドシートと波形フォルダを
入力にキューシートを一括構築する作業は、「(0) 接続確認・台本特定 → (1) マテリアル
登録・キュー作成・カテゴリ設定 → (2) 本体が独立して再取得して機械突合 → (3) 差分が
あれば停止して確認、なければ保存」の順で進めると安定します。途中の中間確認は挟まず、
機械検証がPASSする限り連続実行し、**差分発生時と破壊的操作(既存削除・上書き)の
前だけ**確認を取る設計が実用的です(`SKILL-AUTHORING.md` の「検証→構築→保存→
再検証」の型と対応する、より上位の運用フローです)。

**キューの中身検証は3層+埋め込みIDの整合性まで**: グループ・枠・実体という3階層
構造を持つキューでは、上位2層だけ確認すると「枠はあるが実体が空」を見落とします。
加えて、子要素の名前に埋め込まれた番号が、それが属するコンテナ自身の識別子と
一致しているかも個別にチェックする必要があります。コンテナ名は正しいのに中の
要素名だけ別番号にタイプミスしている、という3層確認だけでは検出できない不整合が
実際に起きます。

**ループ設定はプロパティでなくwav自体のメタデータを疑う**: プロジェクトファイル上に
ループ設定のプロパティが見当たらない場合、ループ再生は素材ファイル自体が持つ
メタデータ(ループ開始/終了位置・無限リピート指定、いわゆる `smpl` チャンク)に
よって制御されていることがあります。新規素材にこのメタデータが無ければ、既存の
ループ素材と同じ構造で埋め込むことでループ再生を実現できます。また、新規
オブジェクト作成はカテゴリ分類やフラグ類などの付随設定を自動継承しないことが
あるため、同じフォルダ内の既存オブジェクトの設定を確認して手動で揃える必要が
あります。

**DAW書き出しwavの無音化バグと調査手順**: 標準的なRIFF/WAVEはヘッダ直後にfmt→
dataという単純な並びですが、一部のDAWは書き出し時に先頭へパディングチャンクや
放送用メタデータチャンクを追加します。これはWAV規格上は合法ですが、一部の
オーサリングツールのインポータはこの非標準的なチャンク並びを正しく解釈できず、
音声データ自体は正常なのに無音として取り込んでしまうことがあります。「鳴らない」
不具合の調査は、正常な比較対象を用意し、キュー設定→枠の紐付き→素材登録→
ディスク実体→バイナリヘッダ構造、と上から下まで機械的に突き合わせるのが有効で、
最終的にバイナリのチャンク構造まで確認して初めて原因が確定することがあります。

**バリエーション数から再生方式が決まる命名規約はチェックリスト化できる**:
「1バリエーション=常に同じ音」「2バリエーション=2択ランダム」「3以上=直前と
重複しないランダム」といった、バリエーション数から再生方式が一意に決まる規約を
持つプロジェクトでは、この対応表を検証時の自動照合ルールとして使えます。
バリエーション数と実際の設定値の不一致を効率的に検出できます。

## その他の実装上の工夫(参考)

- `atomcraft_get_property` は無効フィールドが1つでも混ざると全滅していた
  従来のAPI挙動に対し、`INVALID_FIELD` を検知したフィールドだけ除外して
  再試行を繰り返す部分成功アルゴリズムを実装しています。除外されたフィールドは
  `data.invalid_fields` と `warnings` で通知されるため、レスポンスは必ず
  確認してください
- `catalog.py` はタイプ名・フィールド名のtypoに対して `difflib` による近似
  候補を提示します。オブジェクトタイプやフィールド名を間違えた場合、
  エラーの `hint` に近い候補が入っていないか確認すると早く直せます
