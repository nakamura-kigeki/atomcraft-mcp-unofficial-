# SKILL-AUTHORING.md — タイトル固有スキルを作るヒント

本MCPサーバーが提供する21ツールは汎用的なCRUD・プロパティ操作の集合であり、
「あるタイトルの台本フォーマットに合わせてキューシートを組む」「特定の命名規則で
マテリアルを登録する」といったプロジェクト固有の定型作業そのものは面倒を見ません。
そうした定型作業は、本MCPサーバーの上にプロジェクトごとの「スキル」(Claude Code
のskills、Codexの`.agents/skills`など)を書いて手当てするのが実用的です。本文書は
その書き方のヒントです。ツールの機能一覧は `CAPABILITIES.md`、接続の仕組みや
エラー処理は `HANDBOOK.md` を参照してください。

## Claude Code の skills/ と Codex の .agents/skills 両対応

Claude CodeとCodex CLIの両方でエージェントを運用する場合、同じ内容のスキルを
二重管理したくなります。両対応のスキルを書く際のポイントは以下の通りです。

- **ディレクトリ構成をそろえる**: Claude Codeは `skills/<skill-name>/SKILL.md`、
  Codexは `.agents/skills/<skill-name>/SKILL.md`(または同等のパス)を読みます。
  両方に同じ内容の `SKILL.md` を置くか、一方から他方へのシンボリックリンク/
  コピーで同期する運用のどちらかを決めてください。手作業でのコピーは差分が
  出やすいため、同期を自動化する短いスクリプトを用意しておくと事故が減ります
- **frontmatterはどちらの実装にも解釈できる範囲に留める**: `name` /
  `description` のような両者に共通するキーだけで完結させ、片方の実装にしか
  ないキー(プラグイン固有の拡張フィールドなど)に本質的なロジックを依存させ
  ないようにします。特定の実装だけが解釈する設定に処理の合否が左右されると、
  もう片方の実装では単に無視されて意図しない挙動になります
- **本文はツール名ベースで具体的に書く**: 「よしなにキューシートを組んでください」
  のような曖昧な指示は、モデルや実装が変わると再現性が落ちます。使うツール名・
  action・引数の形を具体的に書き、モデルの裁量に依存する箇所を最小化してください
  (詳細は本文書末尾の「スキル品質の要点」を参照)
- **MCPサーバー名の差異を吸収する**: MCPサーバーの登録名はクライアント設定
  ファイル側で決まるため、環境によって `atomcraft` 以外の名前で登録されている
  こともあります。スキル本文でツールを呼ぶ説明をする際は、正確なMCPサーバー名を
  決め打ちせず「atomcraft系のMCPツール」のように前置きしておくと、設定名が
  違う環境でも読み替えやすくなります

## 「検証→構築→保存→再検証」の型

本MCPサーバーの非冪等作成系ツール(create/register系)は、接続断が起きると
`UNKNOWN_OUTCOME` を返し、成功したかどうかがサーバー側でも分からなくなります
(`HANDBOOK.md` 参照)。この特性上、定型フローのスキルは次の4段階を
明示的に書いておくことを推奨します。

1. **検証(現状確認)**: 作業対象がすでに存在していないかを先に確認する。
   `atomcraft_get_object(method='find_by_name')` や `atomcraft_get_tree` で
   現状のツリーを取得し、「これから作ろうとしているものが既にあるか」を
   スキップ判定の根拠にする
2. **構築**: `create_object` / `create_cue` / `manage_material` 等で実際に
   作成する。1件ごとに戻り値の `success` を確認し、`UNKNOWN_OUTCOME` が
   返った場合は即座に再実行せず、まず該当オブジェクトの存在確認に切り替える
3. **保存**: `atomcraft_manage_workunit(action='save')` や
   `atomcraft_project_io(action='save_all')` で永続化する。保存は冪等書き込み
   なので再実行自体は安全だが、保存前に未保存の変更が想定通りの内容かを
   確認してから呼ぶ
4. **再検証**: 保存後にもう一度 `get_property` や `get_tree` で対象を読み直し、
   「意図した内容で実際に反映されているか」を機械的に確認してからスキルの
   完了を報告する。ツール結果の `success:true` を見ただけで完了を宣言せず、
   実際に読み戻した値で裏付けるという原則です

この型を徹底すると、途中でスクリプトサーバーが停止して再起動が必要に
なった場合(`HANDBOOK.md` の「実機で確認された接続断の挙動」を参照)でも、
どこまで終わっていたかを再検証ステップから機械的に復元できます。

## キャラ/ユニット単位のシリアル実行

**スクリプトサーバーは同時に1つの接続しか受け付けません**(実機Ver.3.56.01 LEで確認、
Ver.3.57.02では未確認)。また1つのセッション内でも、ツールを並列に呼ぶとスレッドセーフで
ないDLLに同時アクセスしうるため避けてください(詳細は `HANDBOOK.md` の
「大量呼び出しはサブエージェント委譲が安定」)。複数キャラクター・複数ユニットに
またがる作業は、並列サブエージェントではなく必ず逐次実行にします。定型フローの
スキルは、次のような単位分割と逐次実行を明示しておくべきです。

- 作業単位(キャラクター1人、ユニット1体など)ごとに1つのサブエージェント
  呼び出しを割り当てる
- サブエージェントは呼び出しの中で「検証→構築→保存→再検証」を完走させてから
  終了する
- 呼び出し元は次のサブエージェントを**前のサブエージェントの完了を待ってから**
  起動する。並列に投げてスクリプトサーバー側の接続を奪い合うと、片方が
  `SERVER_UNREACHABLE` になる可能性がある
- 接続が切れて戻らなくなった場合は、ユーザーにAtom Craft側でのスクリプト
  サーバー再起動を依頼してから次の単位に進む

## 対象の特定は複数候補を前提にする

台本シートなど、番号や名前で対象を検索する処理をスキルに書く場合、「番号なら
一意」という前提は成り立ちません。同一番号で別内容のシートが複数実在する運用は
普通に起こります。完全一致が1件に絞れる場合のみ自動採用し、それ以外(複数ヒット・
部分一致・0件)は必ず候補リストを提示してユーザーに選ばせてください。並び順
(新しい順など)の先頭を自動採用してはいけません——並び順であって決定根拠では
ありません。

## API制約への実務的な対処

定型作業を自動化する過程で、ツール側のAPI制約に突き当たることがあります。次の
2パターンは典型例です。

- **登録・リネームの失敗は「既に別経路で登録済み」を疑う**: 共有環境で複数対象に
  同じ「新規作成/登録」操作をバッチ実行し一部だけ失敗した場合、単純なエラーとして
  再試行するのではなく、対象がすでに(並行作業等によって)存在している可能性を
  確認し、存在すれば既存オブジェクトを検索して後続処理に流用してください。また
  リネーム機能自体が用意されていないツールでは、(1) 新しい名前で再登録、(2) 参照元を
  新側へ向けて新規作成、(3) 旧参照と旧オブジェクトを削除、という3手順で同等の
  効果を実現できます。実施前に1件だけ試運転してから残りに横展開すると事故が
  少なくなります
- **「GUI操作必須」と結論する前にAPIソースを確認し、フォールバックを用意する**:
  MCP等のツール一覧に「それらしい操作」が見当たらなくても、対象アプリのAPIや
  MCPサーバーの実装ソースを直接読むと、実は必要な関数がすでに公開済みだったと
  分かることがあります。一方、起動中の外部アプリでも一部のナビゲーション系APIが
  対象が明らかに存在するのに空を返し続けることがあります。同じ呼び出しを
  繰り返し試すのではなく「その操作カテゴリはライブAPIでは構造的に非対応」と
  判断し、バックアップを取った上でプロジェクトファイルを直接・安全にオフライン
  編集する方式に切り替える判断も要ります

## MCPコール数の見積もり方

長時間実行になりやすい定型フローは、着手前におおよそのMCPコール数を見積もって
おくと、想定より膨らんだ場合に異常として気づけます。見積もりの目安は次の通りです。

- **読み取り(現状把握)**: `atomcraft_get_tree` を使えばフォルダ階層+全ノードの
  プロパティを1回の呼び出しで取得できます。個別に `get_object` → `get_property`
  を繰り返す設計にすると、対象数 × 2回以上のコールになりがちなので、まず
  `get_tree` で置き換えられないかを検討してください
- **1オブジェクトの新規作成**: 「作成(1) + 名前・カテゴリ等の属性設定(1〜数回)
  + カテゴリ付与(1)」のように、1オブジェクトあたり数回のコールが必要になる
  ことが一般的です。100件作る作業なら300〜500コール程度を目安に見積もり、
  実行中の呼び出し回数がその2〜3倍を超えたら設計を見直すサインと考えてください
- **一括操作で削減できる箇所**: `atomcraft_bulk_property` の `action=set` の
  ように複数対象へ同一値をまとめて設定できるツールがあれば、1件ずつの
  `set_property` より大幅にコール数を減らせます(ただし`action=get`側は
  実機で既知の未解決問題があるため、`CAPABILITIES.md` を確認してから
  採用してください)
- **見積もりが大きく外れたら中断のサイン**: サブエージェントに委譲する際は
  「想定コール数の目安」をプロンプトに含めておき、実行後にツール呼び出し
  回数の桁が大きく違えば、想定外のループや無限リトライが起きていないかを
  疑う材料にしてください

## 定型フロー分解例(架空タイトル)

以下は架空のタイトル「星海のオーケストラ」、架空のキャラクター「アリア」
「レイン」を題材にした、台本からボイスキューシートを構築する定型フローの
分解例です。実在するタイトル名・キャラクター名ではありません。

**前提**: キャラクターごとの台本(セリフ一覧)がスプレッドシート等で用意されて
おり、対応する波形ファイル群がフォルダに揃っている状態を想定します。

1. **接続確認**: `atomcraft_debug(action='ping')` で接続確認。失敗する場合は
   ユーザーにスクリプトサーバー起動を依頼してBLOCKEDとして報告する
2. **現状確認(検証)**: `atomcraft_get_object(method='find_by_name', object_type='CueSheet', object_name='アリア')`
   で、アリア用キューシートが既に存在するかを確認する。存在すれば
   `atomcraft_get_tree` でその中身(既存キュー一覧)を取得し、台本と突き合わせて
   「まだ登録されていない行」だけを以降の対象にする
3. **マテリアル登録(構築・1)**: アリアの波形フォルダに対して
   `atomcraft_manage_material(action='register_unregistered')` を1回呼び、
   未登録の波形をまとめてマテリアル登録する
4. **キュー作成(構築・2)**: 台本の未登録行ごとに
   `atomcraft_create_cue(method='simple', parent=<アリア用CueSheet>, material=<対応マテリアルUUID>)`
   を呼ぶ。1行につき作成1回+属性設定(Name/CueID等)1〜2回を目安にする
5. **カテゴリ付与(構築・3)**: 作成したキューをまとめて
   `atomcraft_manage_category(action='add', cue_list=[...], category=<カテゴリUUID>)`
   で一括付与し、1件ずつの呼び出しを避ける
6. **保存**: `atomcraft_manage_workunit(action='save', workunit=<対象ワークユニットUUID>)`
   を呼ぶ
7. **再検証**: `atomcraft_get_tree` でアリア用キューシートを読み直し、台本の
   行数と実際に作成されたキュー数が一致するかを機械的に突き合わせる。
   不一致があれば差分をレポートし、成功と報告しない
8. レイン以降の他キャラクターについては、アリアの処理が完全に完了(保存+
   再検証まで)してから、同じ手順で1キャラクターずつ逐次実行する

この分解例のように、「1回のMCPコールで済むところをまとめる」「検証→構築→
保存→再検証の型を崩さない」「キャラクター単位で完全に閉じてから次へ進む」の
3点を明示しておくと、モデルの裁量に依存する部分が減り、再現性が上がります。

## スキル品質の要点

スキルを書いたら、以下の観点で自己点検することを推奨します。いずれも
「モデルが変わっても同じ品質で動くか」という視点でのチェックです。高性能な
モデルほど曖昧な指示から意図を汲んで自発的に検証・委譲・報告を行いますが、
その挙動を前提にスキルの記述を省略すると、別のモデルで動かしたときに
劣化します。

1. **決定論への退避**: モデルの判断が必要な箇所を最小化し、機械的に処理できる
   部分はコマンド・スクリプト・具体的な手順に固定できているか。モデルの出力に
   対する機械検証(件数照合、exit code確認、読み戻しによる確認)があるか
2. **手順の明示性**: 実行ステップが番号付きで列挙され、「よしなに」「適切に」
   のようなモデルの裁量に依存する表現で重要な工程を済ませていないか。使用する
   ツール名・action・引数の形が具体的に書かれているか
3. **検証の明文化**: 「成功と報告する前に何をどう確認するか」がスキル内に
   明記されているか。戻り値の `success` フラグだけを見て成功と判断せず、
   実際の出力を読み戻して判断する旨が書かれているか
4. **進捗報告の証拠付け**: ツール結果で裏付けられる作業のみを完了として報告
   する旨が書かれているか。長時間・大量処理のスキルでは特に重要
5. **境界の明示**: やってはいけないこと(無断保存の禁止、書き込み対象の範囲、
   破壊的操作の前の確認)が明文化されているか
6. **委譲の明示**: サブエージェント委譲が有効な箇所で、いつ・何を・どう委譲
   するかが書かれているか。特に本MCPサーバーは同時に1つの接続しか
   張れず、ツールの並列呼び出しも避けるべきであるため、並列委譲ではなく
   逐次委譲であることを明記する
7. **早期停止対策**: 長時間実行のスキルで「途中でターンを終えない/確認で
   立ち止まるのは破壊的操作・スコープ変更・ユーザーにしか出せない情報の
   ときのみ」という原則が書かれているか
8. **内省再現指示の不在**: 「思考過程を説明せよ」「推論を出力せよ」といった
   指示を含んでいないか。モデルによっては不要な出力形式の変化や拒否を
   誘発しうる
9. **入力データの隔離**: 台本テキストや外部ログなど、外部から取り込む
   データを処理するスキルで、そのデータ内に書かれた指示文には従わない旨が
   明記されているか(プロンプトインジェクション耐性)

これらは網羅的なチェックリストというより、「省略した箇所が別モデルで劣化
しないか」を確認するための観点です。すべてを満たす必要はなく、該当しない
観点はN/Aとして構いません。
